01 Day One · ~90 minutes · 2 labs Networking fundamentals Not started
Theory

A network is just a set of agreements. Two machines that have never met can exchange data because both sides implement the same layered rules. Learn the layers and almost everything else becomes lookup.

The OSI model — seven layers

OSI is a teaching model. Nothing implements it literally, but the entire industry uses its vocabulary: "that's a layer 2 problem", "we need a layer 7 firewall". Read it bottom-up, the way data actually travels.

#LayerUnit (PDU)ExamplesTypical attack here

5SessionDataNetBIOS, RPC, socketsSession hijacking

A mnemonic that sticks: Please Do Not Throw Sausage Pizza Away (Physical, Data link, Network, Transport, Session, Presentation, Application).

The TCP/IP model — what actually runs

The real internet is built on a four-layer model. It maps onto OSI cleanly enough:

TCP/IP layerCovers OSIProtocolsAddressing used

Transport4TCP, UDPPort numbers

* ARP sits awkwardly between layers 2 and 3 — it maps IP to MAC. Different books place it differently; nobody will fail you for either answer.

Encapsulation — how one message becomes a frame

Every layer wraps the layer above it in a header, like envelopes inside envelopes. The receiving machine unwraps in reverse. This is why a 1-byte HTTP request is never 1 byte on the wire.

You type:      GET /index.html HTTP/1.1

L4  Transport    │  TCP hdr  │           HTTP data            │   ← adds src/dst PORT
L3  Network      │ IP hdr │ TCP hdr │        HTTP data       │   ← adds src/dst IP
L2  Data link    │Eth hdr│ IP hdr│ TCP hdr │  HTTP data │FCS│   ← adds src/dst MAC
L1  Physical      1010110001110101000111010110101110100011...

Header sizes: Ethernet 14 B · IP 20 B · TCP 20 B  =  54 bytes of overhead
before your first byte of actual content.

IPv4 addressing

An IPv4 address is 32 bits, written as four decimal numbers 0–255 separated by dots. Each number is one byte, or octet.

      192   .   168   .    1    .   24
   11000000 10101000 00000001 00011000
   └──────── 32 bits total ────────┘

Mask /24 = 255.255.255.0
   11111111 11111111 11111111 00000000
   └──── network portion ────┘ └ host ┘

The subnet mask tells you where the network portion stops and the host portion begins. Hosts on the same network portion can talk directly, over layer 2. Anything else has to go through a router.

A word on IPv6

128 bits, written as eight groups of four hex digits, with :: collapsing one run of zeros. 2001:0db8:0000:0000:0000:0000:0000:0001 becomes 2001:db8::1. Key differences: no broadcast (multicast instead), no NAT by default, and addresses are usually assigned by the router advertising a prefix. fe80::/10 is link-local — you will see it on every interface.

Lab 1.2

Ping like a diagnostician, not a button-presser

Tools: terminal onlyTime: 20 min Target: your gateway + public DNS

Pinging in a deliberate order tells you where a problem is, not just that one exists. Run these four in sequence.

  1. Ping yourself. Proves your TCP/IP stack is alive. If this fails, nothing else matters.
    terminal
    ping -c 4 127.0.0.1        # Windows: ping -n 4 127.0.0.1
  2. Ping your gateway. Proves layer 1–3 to the router works: cable/Wi-Fi, ARP, and your IP config.
    terminal
    ping -c 4 192.168.1.1      # substitute your own gateway
  3. Ping a public IP. 8.8.8.8 is Google's resolver. This proves routing and NAT work — with no DNS involved.
    terminal

    terminal

Why this matters for cybersecurity

You cannot spot abnormal traffic until normal traffic is boring to you.

Layers give you a triage vocabulary. When an alert fires, the first question is always "what layer is this?" A flood of half-open connections is layer 4. A poisoned ARP cache is layer 2. A malicious HTTP payload is layer 7. The answer determines which tool you reach for and which control should have stopped it.

Subnetting is reconnaissance and it is also defence. An attacker who lands on 10.4.7.19/24 immediately knows there are 253 other hosts worth scanning. A defender who segments that same space into sixteen /28 subnets has just made lateral movement far harder, and given the IDS a much clearer picture of what "crossing a boundary" looks like.

The four-ping sequence is the fastest incident triage there is. It separates "the host is compromised" from "the link is down" from "someone poisoned DNS" in under a minute, before you have opened a single dashboard.

Knowledge check

Answer in your head first, then reveal.

Q1A host is 172.16.5.130/26. What is its network address, and can it reach 172.16.5.100 without a router?

Network 172.16.5.128, and no. A /26 has block size 64, so subnets start at .0, .64, .128, .192. Our host sits in the .128–.191 block; 172.16.5.100 sits in the .64–.127 block. Different subnets, so the traffic must cross a router.

Q2Your laptop shows 169.254.11.8. What happened?

No DHCP server answered. The OS fell back to APIPA link-local self-assignment. Either the DHCP server is down, the pool is exhausted, or you are not actually connected to the network you think you are. You can talk to other APIPA hosts on the same link, and nothing else.

Q3A ping reply comes back with ttl=122. What can you infer?

Probably a Windows host about 6 hops away. Windows starts TTL at 128; 128 − 122 = 6 routers crossed. It is an inference, not proof — TTL can be set to anything — but it is a useful first guess during host discovery, and it is exactly how OS-fingerprinting tools make their initial call.

Theory

Yesterday was addresses. Today is the hardware that reads them, and the three protocols — ARP, DHCP and NAT — that quietly make every network you have ever used actually function.

Hubs, switches, routers

All three forward traffic. The difference is what they look at before deciding where to send it, and that single fact drives everything else about them.

DeviceLayerDecides usingForwarding behaviourSecurity consequence
Hub1NothingRepeats every bit out of every other portEveryone sees everyone's traffic. Effectively obsolete — and a sniffer's dream.
Switch2MAC addressLearns which MAC is on which port, forwards only thereIsolates traffic — until MAC flooding or ARP spoofing defeats it.
Router3IP addressConsults a routing table, forwards between networksThe natural place for ACLs, NAT and the security boundary.
Firewall3–7IP, port, state, contentPermits or denies against a policyEnforcement point. Only as good as its rules.
Access point1–2MACBridges wireless clients onto the wired LANThe radio is the perimeter. Anyone in range is on the wire.
Collision and broadcast domains

Two ideas that explain why hubs died and why routers matter:

  • A collision domain is a set of devices whose transmissions can interfere. A hub is one big collision domain; every switch port is its own.
  • A broadcast domain is everything a broadcast frame reaches. A switch floods broadcasts out of every port, so a whole switch is one broadcast domain. Routers do not forward broadcasts — that is what breaks the domain up, and VLANs do the same thing logically.
            ROUTER  ← breaks broadcast domains here
           ┌───┴───┐
      ┌────┘       └────┐
  SWITCH A          SWITCH B
  │  │  │  │        │  │  │
  PC PC PC PC       PC PC SRV

  Collision domains: 7  (one per switch port)
  Broadcast domains: 2  (one per router interface)

MAC addresses

A MAC address is 48 bits, burned into the network card, written as six hex pairs: 00:1A:2B:3C:4D:5E. The first three bytes are the OUI — the manufacturer. That is genuinely useful: a capture full of Apple OUIs and one Raspberry Pi OUI tells you something.

MACs only have meaning on the local link. Every time a packet crosses a router, the layer 2 header is stripped and rewritten with new source and destination MACs. The IP addresses stay the same end to end; the MAC addresses change at every hop. That one sentence explains most beginner confusion.

ARP — the glue between layer 3 and layer 2

Your machine knows the destination IP. To build an Ethernet frame it needs a destination MAC. ARP is how it asks.

PC-A (192.168.1.24) wants to reach 192.168.1.50

1.  ARP Request   broadcast to ff:ff:ff:ff:ff:ff
    "Who has 192.168.1.50? Tell 192.168.1.24"
    → every device on the LAN receives this

2.  ARP Reply     unicast back to PC-A
    "192.168.1.50 is at 00:1A:2B:3C:4D:5E"
    → PC-A caches it and sends the real frame

There is no authentication anywhere in this exchange.
Anyone on the LAN can answer. That is the whole vulnerability.

Cached entries expire after a few minutes. If the destination is not on your subnet, your machine ARPs for the gateway's MAC instead and hands the frame to the router.

DHCP — the four-step lease

Remember it as DORA. All four messages ride on UDP: client port 68, server port 67.

StepMessageFrom → ToContains
DDISCOVER0.0.0.0 → 255.255.255.255"Is there a DHCP server?" Broadcast — the client has no address yet.
OOFFERserver → broadcastA candidate address, mask, gateway, DNS servers, lease time.
RREQUEST0.0.0.0 → 255.255.255.255"I accept that one." Broadcast so other servers know to withdraw.
AACKserver → clientLease confirmed. The client configures its stack.

DHCP also hands out the DNS server and default gateway. A rogue DHCP server that answers faster than the real one can therefore redirect a victim's DNS and its default route in a single reply — a complete man-in-the-middle with no packet crafting required.

NAT and PAT

You have one public IP and thirty devices. NAT rewrites the source address of outbound packets to the router's public address and remembers the mapping. Because many hosts share one address, the router also rewrites the source port to keep conversations apart — that is PAT, and it is what nearly every home router actually does.

Inside (private)Inside portOutside (public)Translated portDestination
192.168.1.2451422203.0.113.76100193.184.216.34:443
192.168.1.3151422203.0.113.76100293.184.216.34:443

Two consequences worth holding on to. First, NAT is not a firewall, but it acts like a weak one: unsolicited inbound traffic has no table entry, so the router does not know where to send it. Second, in a log full of NATed traffic, one public IP can represent hundreds of users — which is why correlating an incident to a person needs the NAT table, not just the firewall log.

Topologies and VLANs

TopologyShapeTrade-off

A VLAN splits one physical switch into several logical ones. Ports in VLAN 10 cannot reach ports in VLAN 20 without a router, even though they share hardware. This is the cheapest and most effective segmentation control you will meet — and it is exactly what you will build on Day 7.

Why this matters for cybersecurity

Three of the protocols that make a network usable have no authentication at all.

ARP trusts anyone. There is no way for a host to verify that the machine claiming to be the gateway really is. That single design decision is the root of ARP spoofing, and therefore of most local man-in-the-middle attacks. The defence is not "fix ARP" — it is Dynamic ARP Inspection on the switch, which validates replies against the DHCP snooping table.

DHCP trusts whoever answers first. A rogue server on a LAN can hand a victim a poisoned DNS address and a malicious default gateway in one packet. DHCP snooping fixes this by designating which switch ports are allowed to send OFFER messages — everything else gets dropped.

Switches are a security control, and a fragile one. The isolation a switch gives you depends on its MAC table having room. Flood it with thousands of fake source MACs and many switches fail open, flooding all traffic to all ports — turning a switch back into a hub. Port security limits how many MACs a port will learn, which is why it is on every hardening checklist.

NAT changes what your logs mean. One public address in a firewall log can be hundreds of internal users. Attributing activity to a host requires the NAT translation table from the same moment in time — a detail that has sunk more than one investigation.

Knowledge check

Answer in your head first, then reveal.

Q1A packet travels from your laptop, through your router, to a web server. How many times does the source IP change? How many times does the source MAC change?

The source MAC changes at every hop; the source IP changes only if NAT is involved. Layer 2 addressing is rewritten link by link, because MACs are only meaningful on the local segment. The IP header normally survives end to end — except that your home router performs NAT, so it rewrites the source IP once, from your private address to its public one.

Q2Why can't a switch stop a broadcast storm, but a router can?

Because a switch forwards broadcasts by design and a router does not. A broadcast frame is addressed to ff:ff:ff:ff:ff:ff, and a layer-2 switch floods it out of every port in the VLAN. A router works at layer 3 and has no reason to forward a link-local broadcast, so it silently drops it. That is why every router interface — and every VLAN — is a separate broadcast domain.

Q3Your ARP cache shows 192.168.1.1 and 192.168.1.50 both at MAC aa:bb:cc:dd:ee:ff. What is the most likely explanation?

Someone is ARP-spoofing you. A machine has told you it owns both the gateway's address and another host's address, so your traffic to either now goes through them. Innocent explanations exist — a router with a secondary address, or a virtualisation host bridging interfaces — but on a normal LAN this pattern is the classic signature of an active man-in-the-middle, and it is exactly what tools like arpwatch alert on.

Why this matters for cybersecurity

Almost every scan, flood and hijack is a lie told about the handshake.

The attacker's view. A SYN scan sends step 1 and never step 3 — fast, and historically quieter in application logs because no connection is ever completed. A SYN flood sends millions of step 1s from spoofed sources to exhaust the server's half-open table. Session hijacking means guessing sequence numbers well enough that the server accepts an injected segment as legitimate.

The defender's view. Once you can read a handshake, a pile of SYN_RECV sockets, an IDS alert about SYN rate, and a storm of RSTs stop being noise and become evidence with a specific meaning. Detection rules for scanning are written directly against these flag combinations — a Snort rule for a NULL scan literally matches flags:0.

Ports are your inventory. Attack surface is the list of things listening on a non-loopback address. Every hardening standard reduces to some version of "close what you do not need, encrypt what you do". Knowing that 23 is Telnet and 22 is SSH is the difference between reading a scan result and understanding it.

Knowledge check

Answer in your head first, then reveal.

Q1Why is a SYN scan faster and quieter than a full connect scan?

Because it never completes the handshake. After receiving SYN-ACK the scanner sends RST instead of ACK. The connection never reaches ESTABLISHED, so the application on the target is never handed a socket and historically never wrote a log entry — the kernel handled it all. It is also faster: two packets per port instead of four, with no teardown. Modern network-level logging and IDS catch it easily, but the technique's name — half-open scan — comes straight from the state machine.

Q2You connect to a port and get "connection refused" instantly. On another port you get nothing for 20 seconds. What is the difference?

Refused = a RST came back; timeout = silence. A RST means the host is alive and reachable, and deliberately told you nothing is listening there — the port is closed. Silence means a firewall dropped your packet without replying — the port is filtered. That distinction is why scanners report "closed" and "filtered" separately, and why a well-configured firewall drops rather than rejects: silence gives the attacker less information.

Q3Why are UDP services like DNS and NTP favoured for amplification attacks, but TCP services are not?

Because UDP has no handshake, the source address is never verified. An attacker sends a small query with the victim's IP as the source, and the server sends a much larger reply to the victim — amplification factors of 50× or more. With TCP the server's SYN-ACK would go to the victim, who would answer with a RST, and the connection would never establish, so no data volume is ever generated. The fix is the same at both ends: source-address validation at the network edge (BCP 38) and rate limiting on the reflectors.

DNS — turning names into addresses

DNS is a distributed, hierarchical database. No single server knows everything; each one knows who to ask next.

You ask your resolver (usually your router or 1.1.1.1) for www.example.com

  resolver → ROOT server (.)         "who handles .com?"
           ← referral to the .com TLD servers

  resolver → TLD server (.com)      "who handles example.com?"
           ← referral to ns1.example.com

  resolver → AUTHORITATIVE server   "what is www.example.com?"
           ← A record: 93.184.216.34

  resolver → caches the answer for its TTL, then answers you

Your query to the resolver is RECURSIVE ("go find out for me").
The resolver's queries outward are ITERATIVE ("just tell me who to ask next").

Transport and TTL

DNS uses UDP port 53 for ordinary queries — one small datagram each way. It falls back to TCP 53 when a reply exceeds what will fit, and for zone transfers (AXFR). A misconfigured server that allows an AXFR from anyone hands over its entire host list; it is still one of the first things a tester checks.

TTL is how many seconds a resolver may cache an answer. Low TTLs mean fast failover — and also mean malware can move its infrastructure quickly. Caching is why a DNS change "takes time to propagate", and why cache poisoning is so damaging: one bad entry gets served to everyone behind that resolver until it expires.

DoH and DoT wrap DNS in TLS (port 443 and 853 respectively). Good for user privacy; awkward for defenders, because DNS query logs have historically been one of the richest detection sources on a network.

HTTPS and the TLS handshake

HTTPS is just HTTP inside a TLS tunnel. TLS gives three things: confidentiality (nobody can read it), integrity (nobody can alter it undetected), and authentication (you are talking to who you think you are). Only the third one relies on certificates.

  CLIENT                                          SERVER
    │  TCP three-way handshake completes first     │
    │                                              │
    │  ClientHello                                 │  TLS versions, cipher
    │ ───────────────────────────────────────────> │  suites, random, SNI
    │                                              │
    │  ServerHello + Certificate                   │  chosen cipher,
    │ <─────────────────────────────────────────── │  cert chain, key share
    │                                              │
    │  client verifies the certificate chain        │
    │   · signed by a trusted CA?                  │
    │   · name matches the host?                   │
    │   · not expired, not revoked?                │
    │                                              │
    │  key exchange → shared session key            │
    │ ←──────────────────────────────────────────> │
    │                                              │
    │       encrypted application data (HTTP)      │

SNI — the hostname — is sent in the clear in the ClientHello (unless ECH is used).
That is how a network filter can block one site on a shared IP, and how a
monitor still knows which sites you visited even over HTTPS.

Your browser trusts a set of root CAs shipped by the OS or the browser itself. A certificate is trusted if a chain of signatures leads from it back to one of those roots. This is also the mechanism behind corporate TLS inspection: install a company root CA on the endpoint, and a proxy can legitimately decrypt everything — which is worth understanding both as a defender and as a privacy question.

Why this matters for cybersecurity

DNS is the most useful log source you have, and the most abused protocol you own.

Nearly every attack starts with a name. Phishing links, malware command-and-control, exfiltration channels — almost all of them resolve a domain first. That makes DNS logs the highest-yield detection source in most environments: newly registered domains, algorithmically generated names, absurdly long subdomains, and TXT-record floods are all visible there before anything else fires.

Poisoning and tampering are cheap and effective. Because a resolver accepts the first answer matching the transaction ID and port, an attacker who can guess or observe both can plant a false address that persists for the whole TTL — for every user behind that resolver. DNSSEC signs records to prevent this; adoption is still partial, which is why the attack still matters.

HTTPS protects content, not metadata. TLS stops an eavesdropper reading the page. It does not hide the destination IP, and unless Encrypted Client Hello is in use, it does not hide the SNI hostname either. Assume an observer knows every site you visited and roughly how much data you exchanged — that is the honest threat model, and it is the basis of most encrypted-traffic analysis.

The redirect is the weak point. Typing example.com sends a plaintext HTTP request before the redirect to HTTPS ever happens. An attacker on the path can intercept that first request. HSTS exists precisely to close that window by telling the browser never to try HTTP for that host again.

Q1A user reports that one website is unreachable, but ping 8.8.8.8 works fine. What do you check first, and why?

DNS. A successful ping to a raw IP proves routing, NAT and the physical path all work — the only major variable left is name resolution. Run dig or nslookup against the site, then against a second resolver such as 1.1.1.1. If one resolver answers and the other does not, or they return different addresses, you have isolated the fault to DNS rather than the network. This is the Day 1 four-ping sequence applied to a real ticket.

Q2You are monitoring a network and see a host making hundreds of TXT queries per minute for long, random-looking subdomains of one domain. What is happening?

DNS tunnelling — almost certainly exfiltration or command-and-control. The data is encoded into the subdomain labels of queries that only the attacker's authoritative nameserver ever sees, with replies smuggled back in TXT records. It works because DNS is allowed out of nearly every network, even when everything else is blocked. The tells are exactly what you observed: abnormal query volume to a single domain, unusually long names, and heavy TXT usage — which is why those three display filters are in Lab 4.3.

Q3If TLS encrypts everything, how can a corporate firewall block access to a specific HTTPS website?

By reading the SNI field in the ClientHello, which is sent before encryption begins. The client must tell the server which hostname it wants so the right certificate can be presented, and in standard TLS that name travels in cleartext. A filter can match on it and reset the connection. The alternatives are DNS-level blocking, or full TLS inspection with a corporate root CA installed on the endpoint. Encrypted Client Hello is designed to close the SNI gap, which is why its rollout is contentious among network defenders.

Why this matters for cybersecurity

Almost every control here exists because a protocol from Days 1–4 trusts something it should not.

Layer 2 is the soft underbelly. Perimeter firewalls do nothing about ARP spoofing, MAC flooding or rogue DHCP, because none of that traffic ever reaches the perimeter. The controls that do work — DHCP snooping, Dynamic ARP Inspection, port security, 802.1X — all live on the access switch. That is why "assume breach" thinking starts with the LAN, not the edge.

Rule order is a vulnerability class of its own. Lab 5.1 step 6 and Lab 5.3 step 6 are the same bug on paper and on a router. Real firewall audits find shadowed rules, forgotten temporary permits, and any any entries that someone added at 2am during an outage and never removed. Reading rule sets critically is a genuinely employable skill.

Segmentation limits blast radius. You cannot prevent every compromise. You can decide what an attacker reaches after the first one. A flat network turns one phished laptop into domain-wide access; a segmented one turns it into an alert and a contained incident. This is the single highest-value architectural control on this list.

Detection needs a defined normal. Every signature you wrote today encodes an assumption about what should never happen — no TCP flags, RDP from outside, Telnet at all. Days 1–4 gave you the definition of normal; today turns it into a rule.

Knowledge check

Answer in your head first, then reveal.

Q1Your organisation has a next-generation firewall at the perimeter. An attacker on the guest Wi-Fi ARP-spoofs a finance laptop and captures its traffic. Why did the firewall not help?

Because the traffic never crossed it. ARP spoofing is a layer-2 attack between two hosts on the same broadcast domain — the frames go host → attacker → gateway without ever traversing the perimeter. A firewall can only filter what passes through it. The real controls are on the switch and in the network design: Dynamic ARP Inspection, DHCP snooping, and putting guest Wi-Fi in its own VLAN that cannot reach the corporate one at all.

Q2Why does a stateful firewall let a web server's reply back in when there is no explicit inbound rule for it?

Because it recorded the outbound connection in its state table. When your machine sent a SYN to 93.184.216.34:443, the firewall stored that four-tuple. The returning SYN-ACK matches an existing entry, so it is permitted as part of an established flow rather than evaluated as new inbound traffic. This is why stateful firewalls need far fewer rules than packet filters, and why the Cisco ACL in Lab 5.3 needed an explicit established line — a basic ACL has no state and cannot infer it.

Q3An IPS would block an attack that an IDS only reports. Why would anyone deploy an IDS?

Because a false positive on an IPS is an outage. The IPS sits inline: if a badly tuned rule matches legitimate traffic, it drops that traffic and business stops — and the IPS itself becomes a single point of failure and a source of latency. An IDS sits out of band on a SPAN port, so the worst case is a noisy alert. The normal path is to deploy a new signature in IDS mode, tune it against real traffic until the false-positive rate is acceptable, and only then promote it to blocking. Confidence in the rule, not capability of the device, decides the mode.

    Good ones to start with: any telnet capture (cleartext session you can read end to end), an http capture, and a dns capture. If you cannot download, use day6-baseline.pcapng from Lab 6.1 and treat it as unfamiliar.

  2. Run the five-step method on it without looking at the filename or description first. Write your answers down before reading anything about the file.

    Scope → composition → who → zoom → timeline. Working blind is the point: in a real incident nobody tells you what the capture contains.

  3. Do the same analysis from the command line, so you can do it over SSH on a server with no GUI.
    bash
    tshark -r sample.pcap -q -z io,phs                    # composition
tshark -r sample.pcap -q -z conv,tcp | head -20       # top conversations
tshark -r sample.pcap -Y "http.request" \
       -T fields -e http.host -e http.request.uri     # every URL requested

       -T fields -e dns.qry.name | sort -u            # every name looked up

    That last one — a unique, sorted list of every domain queried — is often the single most useful line of output in an entire investigation.

  4. Pull a file out of the capture. File → Export Objects → HTTP.

    Every file transferred over unencrypted HTTP can be reconstructed and saved to disk. This is how analysts recover malware samples from a capture — and a concrete demonstration that "the download was over HTTP" is a finding, not a footnote.

  5. Write a three-sentence summary of the capture: who talked to whom, over what, and whether anything looked wrong.

    If you can do that reliably for an unfamiliar pcap, you have the core skill this day was for. Practise it on a new sample capture once a week and it becomes fast.

Why this matters for cybersecurity

The packet capture is the only source that cannot lie to you.

Logs are a summary; packets are the evidence. An application log records what the application chose to record — and malware routinely disables or edits logs. A capture taken at a network tap records what actually crossed the wire, including the traffic no host wanted to admit to. When log and capture disagree, the capture wins.

Lab 6.2 is the argument for encryption, made concrete. Once you have watched your own password appear in a packet, "use HTTPS", "kill Telnet" and "no plaintext protocols on the LAN" stop being policy items and become obvious. It is also the exact evidence that makes a finding land in a report.

Everything from Days 1–5 is visible here. The handshake, the ARP exchange, the DNS query, the TLS ClientHello, the scan, the retransmission storm — Wireshark is where the theory becomes something you can point at. This is why traffic analysis appears in almost every blue-team job description.

Encrypted does not mean invisible. Volume, timing, destinations, packet sizes and SNI all survive TLS. Beaconing, exfiltration and tunnelling are routinely detected in fully encrypted traffic on those signals alone — which is why the IO Graph and Conversations views matter as much as reading payloads.

Knowledge check

Answer in your head first, then reveal.

Q1You applied the capture filter tcp port 80 for an hour, and now you need to check the DNS queries from that period. What can you do?

Nothing — the DNS traffic was never recorded. A capture filter discards packets before they are written, and that decision is irreversible. This is the single most expensive Wireshark mistake, because you usually discover it when the incident is already underway. The habit that avoids it: capture wide (no filter, or something broad like host 10.0.0.5), use ring buffers to bound the disk usage, and do all your narrowing with display filters afterwards.

Q2In Protocol Hierarchy you see 4% of a corporate capture is Telnet. Why does that one number matter so much?

Because Telnet is entirely cleartext, so every one of those sessions exposed credentials. Anyone with a capture position — a compromised switch, an ARP spoofer, a monitoring port — has the usernames and passwords for whatever those sessions logged into, which on a corporate network is usually network equipment with administrative access. It is a finding you can act on immediately: identify the devices, replace Telnet with SSH, and treat every credential used over it as compromised. You will do exactly this on Day 7.

Q3A host sends 400 bytes to the same external IP every 30 seconds, all day, over TLS. You cannot read any of it. Should you care?

Yes — that regularity is a beacon, and you do not need to decrypt it to say so. Human-driven traffic is bursty and irregular; a fixed interval with a near-constant payload size is a machine checking in with a controller. The metadata alone gives you a detection: destination, interval, size and duration. Next steps are to pivot on the destination IP and its SNI hostname, check reputation, look at what process on the host owns the socket, and check whether other hosts show the same pattern. This is the core of encrypted traffic analysis.

Knowledge check

Answer in your head first, then reveal.

Q1You fixed F-01 by enabling SSH but left transport input telnet ssh on the VTY lines. Is the finding closed?

No. Offering both protocols means Telnet is still accepted, and anything — a legacy script, an old management tool, a user's habit — can still use it and still expose credentials. Availability of a secure option does not remove an insecure one. Closing the finding requires transport input ssh, and then verifying that a Telnet attempt is actually refused. This is the general principle behind disabling TLS 1.0, SMBv1 and every other deprecated protocol: the fix is removal, not the existence of an alternative.

Q2Your ACL denies guest traffic to the server VLAN, but you applied it outbound on Gi0/0.20 instead of inbound on Gi0/0.30. Does it still work, and does it matter?

It mostly works, but it is the wrong place. Filtering as close to the source as possible means unwanted traffic is dropped before it consumes any resources on the rest of the path, and one inbound ACL on the guest sub-interface covers every destination at once. Filtering outbound at the server VLAN means the traffic still crosses the router, still hits the CPU, and any other internal subnet you add later is unprotected until you remember to write a second rule. The principle is standard: extended ACLs go as close to the source as you can put them.

Q3A client reads your report and asks: "We have a firewall. Why did any of this happen?"

Because every finding was internal, and the firewall only sees traffic crossing the perimeter. Guest-to-server traffic, Telnet to the switch, ARP spoofing and rogue DHCP all happen inside the LAN and never reach the edge device. This is the practical meaning of defence in depth: the perimeter firewall handles north-south traffic, while VLANs, ACLs, port security, DHCP snooping and DAI handle east-west traffic. A network with a strong edge and a flat interior is exactly the shape that turns one compromised laptop into a company-wide incident.

Final assessment

Twelve questions

One attempt per question — pick the answer you believe before you click. Every question maps to a day you have already done.

01At which OSI layer does a switch make its forwarding decision?

A switch reads the destination MAC address, which lives in the layer-2 frame header. Routers work at layer 3 on IP addresses; hubs do no decision-making at all.

02What is the network address of 192.168.4.130/26?

A /26 has a block size of 64, so subnets start at .0, .64, .128 and .192. The address .130 falls in the block beginning at .128, which runs to a broadcast of .191.

03A host shows the address 169.254.8.12. What happened?

169.254.0.0/16 is APIPA link-local space. Seeing it means DHCP failed — the server is down, the pool is exhausted, or the host is not on the network it thinks it is.

04Which packet is the second step of the TCP three-way handshake?

The server answers the client's SYN with a combined SYN-ACK: it acknowledges the client's sequence number and offers its own. The client's ACK is step three.

05Which port should never be open on a modern network, because everything it carries is cleartext?

Telnet sends credentials and session data unencrypted — you recovered a password from a Telnet capture on Day 7. SSH on port 22 is its encrypted replacement.

06You get an instant "connection refused" on one port and a 20-second timeout on another. What is the difference?

A RST proves the host is alive and nothing is listening on that port. Silence means a firewall dropped the packet without replying — which is why hardening guides prefer DROP over REJECT.

07Which control is designed specifically to stop ARP spoofing?

DAI validates ARP replies against the DHCP snooping binding table and drops forged ones. A perimeter firewall never sees this traffic — it stays inside the broadcast domain.

08Which Wireshark display filter isolates connection attempts — the shape of every port scan?

SYN set with ACK clear is only true for the first packet of a connection. Option B is valid BPF capture-filter syntax, not display-filter syntax — a distinction worth keeping straight.

09A ping reply arrives with ttl=118. What is the most reasonable inference?

Windows starts TTL at 128, so 128 − 118 = 10 routers crossed. It is an inference rather than proof — TTL can be set arbitrarily — but it is how OS fingerprinting makes its first guess.

10Even over HTTPS, what can a network observer normally still determine?

TLS protects content, not metadata. The SNI field in the ClientHello carries the hostname in cleartext unless Encrypted Client Hello is used — which is how a filter can block one site on a shared IP.

11An ACL begins with permit ip any 10.10.30.0/24 any and a deny tcp any host 10.10.30.5 eq 23 sits two lines below. What happens to Telnet?

ACLs are evaluated top down and stop at the first match. A broad permit above a specific deny shadows it completely — the single most common firewall misconfiguration, and the reason hit counters are worth reading.

12A host sends 380 bytes to the same external IP every 30 seconds, all day, over TLS. What is your call?

Human traffic is bursty and irregular; a fixed interval with near-constant payload size is a machine checking in. You do not need to decrypt anything — destination, interval, size and duration are enough to justify investigating.

Keep reading captures

Static routes, OSPF and BGP — plus how BGP hijacking works. Packet Tracer and GNS3 both handle this comfortably, and your Day 7 topology is a good starting point.

A spare machine, VirtualBox or Proxmox, pfSense or OPNsense as the firewall, Security Onion for IDS. Everything free, and it turns theory into muscle memory.
